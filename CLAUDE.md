# Valan

Mobile app that lets second-hand sellers publish a listing once and manage it across several marketplaces. First niche: music (vinyl, CDs, cassettes, audio equipment).

Full product brief (scope, flows, marketplaces, open questions): @docs/PROJECT_BRIEF.md

## Stack

- App: React Native with Expo, TypeScript. iOS only in v1.0.
- Backend: Supabase — Auth, Postgres with RLS, Storage, Edge Functions, scheduled jobs.
- Payments: RevenueCat (subscription via in-app purchase).
- Marketplaces: eBay and Discogs in v1.0. Reverb and Etsy later.

## Commands

- Node 22 or later (`.nvmrc`; CI reads the same file). Install: `npm install`
- Run: `npx expo start`
- Lint: `npm run lint`
- Type check: `npm run typecheck`
- Tests: `npm test` (app) · `npm run test:db` (RLS, pgTAP) · `npm run test:integration` (services against the local Supabase; needs `npx supabase start`, which runs the database, auth, storage and the Edge Functions) · `npm run test:functions` (Edge Functions, Deno)
- Local database (needs Docker running): `npx supabase db start` · apply all migrations from scratch: `npx supabase db reset`
- Types, after every migration: `npx supabase gen types typescript --local > src/types/database.ts` (CI fails if the file is out of date)
- Deploy migrations to the linked project: `npx supabase db push`
- Switch environment: `npx supabase link --project-ref <staging or production ref>`. Database commands act on the linked project, so check which one is linked before pushing.

## Structure

- `src/app/` — Expo Router routes only: every file is a screen, `_layout.tsx` files define navigators. `(tabs)/` holds the four tabs; `new-listing/` and `subscription` open as modals. No test files here.
- `src/components/` — base UI components (`Screen`, `ScreenTitle`, `AppText`, `Button`, `ListRow`, `Tag`, `TextTabs`, `SegmentedControl`, `TabBar`, `SummaryStrip`, `Thumbnail`, `ItemPhoto`, `MarketplaceRow`, `OfferCard`, `Wave`, `ScreenMessage`, `Notice`, `TextField`, `PriceField`, `CheckRow`, `SwitchRow`, `BackLink`, `ChipGrid`, `PhotoGrid`, `EvenGrid`, `FlowHeader`). Screens are built from these. `Screen` takes an optional `header`, `footer` and `scroll` for the steps of a flow. `ScreenMessage` is the shared block for empty, error and offline states.
- `src/features/<screen>/` — pure functions a screen needs to turn rows into what it shows (labels, filters, totals), with their tests. No React here.
- `src/constants/theme.ts` — design tokens (colours, text roles, spacing, radii, control heights). Screens use these, never raw values.
- `src/hooks/` — React hooks, including the ones that load a screen's data from the services (`use-listings-overview`) and `use-is-online`. `use-listing-draft` holds the one draft the new-listing steps share and what became of it when published; `use-loadable` is the one load/reload/refresh state machine (loading, error to retry, ready, a refresh that keeps what is on screen), which `use-listings-overview`, `use-listing-detail` and `use-offers` are built on, and `use-refresh-on-focus` refreshes a screen when the seller comes back to it; `use-reopened-draft` loads a saved draft; `use-guarded-action` runs a request to the server so the same one is never started twice at once (a key per request, a ref as the guard). `*.web.ts` files are the browser variant (the browser is a development preview only).
- `src/app/dev/` — development-only screens, such as the component gallery at `/dev/components`; they redirect to the home screen in production builds.
- `src/i18n/` — translations: `t(key, values)` and one dictionary per language in `locales/`; `{name}` in a string is filled from `values`.
- `assets/images/` — app icons and drawn marks (`wave-line.svg`). `assets/samples/` — a stand-in sleeve image used only by the development gallery. SVG files are shown through `expo-image`, coloured with theme tokens via `svgVariables`.
- `assets/locales/` — the iOS permission texts in each language, wired through `locales` in `app.json`.
- `__mocks__/` — Jest stand-ins for native modules that have none under test (`expo-network`).
- `src/services/` — the service layer; the only place the app calls Supabase (enforced by a lint rule). `getSupabase()` in `supabase.ts` is the single client; `session-storage.ts` keeps the session encrypted. `listings.ts`, `drafts.ts` and `listing-detail.ts` read and write the real `items` table (through `requireUserId()`, so a call with nobody signed in fails plainly). `catalogue.ts`, `marketplaces.ts`, `connections.ts` and `publishing.ts` are still stand-ins shaped like the final services; `offers.ts` and `sales.ts` return nothing, so a real account shows no invented offers or sales (`offers.ts` already has the final types, the `OfferError` kinds the screen has words for, and `respondOffer` waiting for its Edge Function). `external-link.ts` opens a marketplace page, and only a secure `https` address. `photo-picker.ts` wraps the camera and photo library (`expo-image-picker`), `photo-files.ts` re-encodes a picked photo (`expo-image-manipulator`), and `photos.ts` stores and shows photos.
- `supabase/migrations/` — schema changes. `supabase/tests/` — pgTAP tests for RLS and data rules.
- `supabase/functions/` — Edge Functions (Deno, excluded from the app's lint, type check and Jest). `_shared/connectors/` holds the connector interface (`types.ts`), the in-memory `fake.ts`, `contract.ts`, the test suite every connector must pass, and `discogs.ts` (connecting only, so far). `_shared/token-cipher.ts` encrypts stored marketplace credentials; `_shared/connections/` holds the store of connections and connection attempts (`store.ts`, the only code that reads or writes those tables) and the stand-ins its tests use; `_shared/server.ts` is how the connection functions reach Supabase and their settings. Each function keeps its rules in a file tested without a server (`connect-start.ts`) and wires them in `index.ts`.
- Tests live next to the code in `__tests__/` folders; navigation tests are in `src/__tests__/`.
- `src/types/` — `expo.d.ts` loads Expo's ambient types for `npm run typecheck` (Expo's own `expo-env.d.ts` is generated and git-ignored); `database.ts` holds the generated Supabase types, never edited by hand.

## Project decisions

- The app never calls eBay or Discogs directly. It calls Supabase Edge Functions, which hold the users' marketplace tokens.
- Each marketplace is a connector behind one interface: startConnect, finishConnect (OAuth is two steps; it returns the credentials and the name of the account), publish, update, remove, listOrders, listOffers, respondOffer, plus a declaration of what it supports. Connectors throw only `ConnectorError`, with a `kind` the caller can act on.
- The app writes only `profiles` (language and currency), `items`, `item_photos` and `push_tokens`. `platform_connections`, `listings`, `offers` and `sales` are written by Edge Functions; the app can read them, except the token columns, so queries on `platform_connections` must name their columns.
- The app can delete an item only while it is a draft and can never write `items.status`; publishing, selling and removing an item go through Edge Functions, so app inserts and updates on `items` must not send `status`.
- A sale is a permanent record: it keeps a snapshot (`marketplace`, `item_title`, `item_artist`) and survives the deletion of its listing or item (`listing_id` becomes null). Only deleting the account deletes sales.
- Every table carries `user_id`; child tables use a composite foreign key so a row cannot belong to a different user than its parent.
- A record keeps the `format` and `release_year` of its catalogue release and is graded on the Goldmine scale (`media_condition`, `sleeve_condition`). Equipment has its own `equipment_condition` and none of the record fields; check constraints enforce both.
- The equipment condition is Valan's own scale: new, like_new, good, fair, for_parts, best to worst. The database never stores a marketplace's condition values; each connector maps Valan's scale to its marketplace, and several of ours may map to one of theirs. The contract tests require every connector that lists equipment to map every value. Finer values (excellent, very_good, poor) may be added later, for Reverb; nothing is removed.
- The eBay connector checks which conditions are valid for the listing's category against the eBay API; it never assumes them.
- Marketplace names, and what each marketplace can list, are never written into a screen or a translation. Each connector declares its capabilities (`itemTypes`, `requiresCatalogueRelease`, `respondToOffers`); the app reads the same shape from `src/services/marketplaces.ts` and builds the notice, its tag ("Só {name}" when one marketplace is left, "Sem {excluded}" when two or more are) and the "Publica em" list from it, so a new marketplace needs no new copy.
- A marketplace's requirements may limit where a listing goes, but never stop the seller from listing elsewhere; the app always says which marketplaces are excluded and why. Discogs accepts only records chosen from its catalogue, so a listing without a catalogue release (a record the catalogue lacks, or any other item) is valid and goes to eBay only. In the publish step an unavailable marketplace is shown disabled with the reason, never hidden (`marketplaceReach` in `src/features/new-listing/draft.ts`, `reachNotice` in `labels.ts`).
- New-listing step 1 is one field, "O que vais vender?". Catalogue editions appear as suggestions while the seller types; choosing one makes the item a record linked to that release. Without one (none of the editions, no results, or a failed or offline search) the seller continues with the typed name and only then says whether it is a record or another item, which picks the condition scale. The catalogue never blocks the flow.
- Money is stored in minor units (`price_minor`, `amount_minor`, `fees_minor`) with a currency code.
- App configuration: `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_PUBLISHABLE_KEY`.
- Data model: profiles, platform_connections, connection_handshakes, items, item_photos, listings, offers, sales, push_tokens.
- When an item sells on one marketplace, its listing is removed from the others.
- Records are identified through the Discogs catalogue (search or barcode). Equipment has no catalogue step and goes to eBay only.
- Sign-in: email, Sign in with Apple and Sign in with Google, all through Supabase Auth. Apple and Google buttons have equal prominence. Account deletion inside the app.
- Email sign-up is confirmed with a 6-digit code typed in the app, not a link (`otp_length = 6` and `supabase/templates/confirmation.html`, which picks its language from the device that signed up). Sign-up answers the same for a new and an existing email, and sign-in gives one message for a wrong email or password, so the app never reveals whether an account exists. The one exception is by design: with the right password and an unconfirmed email, the seller is told to confirm.
- `src/services/auth.ts` is the only place that talks to Supabase Auth; it returns outcomes with a reason (`AuthFailure` in `src/features/auth/rules.ts`), never raw errors. `SessionProvider` (`src/hooks/use-session.tsx`) holds who is signed in. The root layout shows nothing until the stored session is read, then only the screens that fit: `src/app/welcome/` (entry, email form, code, and resetting a password) for a signed-out visitor, everything else for a signed-in seller. Hiding screens is for the seller's sake; the database is what protects the data. A new top-level route must be added to the right `Stack.Protected` group in `src/app/_layout.tsx`.
- A forgotten password is reset with the same kind of emailed 6-digit code (`supabase/templates/recovery.html`): `requestPasswordReset` answers the same whether or not the email has an account, and `resetPassword` checks the code, stores the new password, signs the seller in and ends the sessions on every other device. The server then emails "your password was changed" (`password_changed.html`). Confirming the code creates a session before the new password is stored, so `src/services/auth.ts` holds session changes back until the reset is over (`withSessionChangesHeld`); an integration test proves nobody hears of the session in between. If the server refuses the new password the code is spent, the seller is signed out and has to ask for another. Changing the password while signed in is not built; it belongs to the Conta screen and must ask for the current password first.
- Deleting an account is done by the Edge Function `delete-account` (`supabase/functions/delete-account/`). It and the connection functions are the only code that uses the service-role key. It acts only on the account its caller's session token belongs to, whatever the request says, and asks for the current password again, which it checks on the server. It deletes the seller's photo folder first and the user second (the database then deletes their rows in every table, sales included); if the photos fail the account is kept, so nothing is orphaned and asking again finishes the job. The rules live in `delete-account.ts`, tested without a server; `index.ts` wires them to Supabase. The app calls it through `deleteAccount(password)` in `src/services/auth.ts`, from `src/app/delete-account.tsx`, which says what is lost and confirms once more. When marketplace accounts are connected for real, deleting must also revoke that access and take the published listings down first (`docs/standards/security.md`); sellers who sign in with Apple or Google will need another way to confirm than a password.
- Staging stays on Supabase's default email sender until the founder configures a custom SMTP provider in the dashboard; the default sender does not allow the code template. Until then the code flow is tested only against the local stack, and `supabase config push` must not be run: `supabase/config.toml` is ahead of staging on purpose (code length, expiry, the confirmation and recovery templates, the "password changed" notice).
- Unit tests never reach Supabase: `jest.setup.js` replaces the auth service with a signed-in stand-in. Services are tested for real against the local stack (`npm run test:integration`, which refuses any URL that is not local and reads the local keys at run time, never from a file).
- The new-listing flow keeps one draft across its steps (`ListingDraftProvider` in `src/app/new-listing/_layout.tsx`). Leaving the flow, by Cancel or by swiping the sheet down, saves it as a draft item when it has a release or a title; if the save fails the seller chooses between retrying and leaving without saving. A draft is not kept if the app is killed mid-flow.
- A record needs its media condition to move past step 2; the sleeve condition is optional. Photos: up to 8.
- New-listing step 3 takes the price (stored in cents; `parsePrice` accepts digits with up to two decimals after a comma or point), whether offers are accepted, and the marketplaces. Every supported marketplace has a row: ticked by default when the listing can go there and the account is connected; otherwise shown disabled with the reason (not connected, or excluded by the marketplace's requirements). Fee estimates use each marketplace's `feeRate` and are labelled as estimates.
- Publishing goes through `src/services/publishing.ts` (fake for now): one outcome per marketplace, with a reason code the app has words for. Step 4 shows each outcome and retries one marketplace at a time. Once an item is sent, or on its way, it is no longer saved as a draft on leaving; if the request itself fails, the draft is still there and is saved under the same item id. The sample publish service makes eBay refuse the first attempt (missing shipping policy) and accept the retry, to show the error path of mockup 07.
- What is real and what is not, for now: items are real rows (list, save a draft, delete a draft, read one). Publishing is still a stand-in: it saves the item for real as a draft and invents the marketplace outcomes, so a "published" item shows under Rascunhos. Pausing, resuming, removing and retrying a listing change what is on the marketplaces, which only the server may do; until the Edge Functions exist the detail screen shows them as coming soon and they do nothing. 
- `saveDraft` inserts the item and, when the id already exists, updates the columns the app may write. A plain upsert is refused by the column grants (the app may not update `id` or `user_id`).
- Photos are stored when a draft is saved or published, not when they are picked. Each photo gets its id on the device (`newPhotoId`) and is re-encoded before upload (`src/services/photo-files.ts`): a JPEG of at most 1600 px on the longest side, and a small one of at most 320 px beside it. Rows and thumbnails load the small one, the screen of one item the full one. Re-encoding is also what drops the location the camera wrote.
- Files live in the private `item-photos` bucket under `{user id}/{item id}/{photo id}.jpg` (and `-small.jpg`). The bucket takes JPEG only, up to 5 MB. Storage policies let a signed-in user add, read and delete only under their own folder; there is no update, so a stored photo is never overwritten. `item_photos` holds one row per photo, at most eight per item, each in its own position.
- Stored photos are shown through signed addresses that last an hour. Every photo carries a stable cache key (its photo id, with `-small` for the small version), so a new address does not download it again; pass it on wherever a photo is shown (`{ uri, cacheKey }`).
- Saving a draft makes its stored photos match it: new ones are uploaded, removed ones are deleted with their files, and the order is rewritten in one statement. A photo that fails to upload is counted and left out; the item and the others are saved, and the seller is told how many are missing. Publishing goes ahead only with every photo stored.
- Deleting a draft deletes its photo files first, then the item (the rows go with it). The app can reach only its own files, so a failure in between leaves orphans; see the release tasks in `docs/PROJECT_BRIEF.md`. The real publish function must send the marketplaces only the re-encoded files from the bucket.
- Services throw real `Error`s, never the plain objects Supabase returns (`toError` in `src/services/errors.ts`).
- A unit test can never reach a Supabase project: `jest.setup.js` replaces `src/services/supabase.ts` with a stand-in that throws. A service that queries Supabase is tested in `src/services/__integration__/` against the local stack, with two real users where isolation matters.
- An item gets its id on the device when its draft starts (`newItemId` in `src/services/ids.ts`), and every save and publish carries it. Saving a draft and publishing are idempotent per item id, and publishing per item id and marketplace (the schema has unique `(item_id, marketplace)` on listings): publishing the same draft twice, or saving it as a draft after a publish attempt, must never create a second item or a second listing. A marketplace that already has the listing is left alone; one that refused is tried again. Saving never changes the status or the listings of an item that was sent. The fake services behave this way; the real Edge Function must too.
- Publishing belongs to the server. Each marketplace's listing is `pending` until the marketplace answers, and meanwhile the item shows in Anúncios with the "a publicar" tag. The seller can always leave: the result screen has a way out while publishing, and after 30 seconds without an answer it says so ("Ainda a publicar. Podes sair; o estado aparece em Anúncios."). The real publish function must therefore create the item and its pending listings first and answer per marketplace afterwards, and must not depend on the app staying open.
- No confirmation before publishing; confirmations are for actions that cannot be undone or that commit the seller to a sale (see `docs/standards/ux.md`).
- Prices in lists use Inter semi-bold 17 with tabular figures (`Type.rowPrice`); Fraunces stays for titles, the summary figures, the sales total, the price field and the one number a card or screen is about (the price on an item's own screen, the offered price on an offer card).
- The pending-offers count has one source, `PendingOffersProvider` in the tabs layout (`src/hooks/use-pending-offers.tsx`). The tab badge and the listings summary both read it, and a refresh of the listings recounts it.
- The Propostas tab (`src/app/(tabs)/offers.tsx`) has two tabs, "Pendentes · n" and "Respondidas", built from `OfferCard`. An offer past its `expires_at` counts as expired in the app whatever its stored status, so it is answered nowhere and sits under Respondidas; the server decides the same. Whether the app can answer an offer comes from the marketplace's `respondToOffers` capability, never from its name: when true the card has Rejeitar and Aceitar, when false one button opens the marketplace (the offer has no page of its own in the schema yet, so it opens the listing), and with nowhere to send the seller the card says where it can be answered. Accepting commits the seller to a sale, so it asks first, naming item, buyer and amount; rejecting does not. `respondOffer` sends the amount the seller saw and the server refuses a changed one; asking twice with the same answer is safe, the opposite answer is refused (`OfferError` kinds: not_found, expired, already_answered, unsupported, changed, unavailable). In the real app only the server writes `offers`, the sale is recorded when the marketplace reports the order, and the other listings are removed then.
- The listing detail's "Ver" opens Propostas with `?offer=<id>`, which selects the tab that offer is on and brings it into view once. "Continuar rascunho" opens the new-listing flow at step 2 with `?draft=<id>` (loaded through `use-reopened-draft`); Back from step 2 goes to step 1 by name, where the seller can still pick a catalogue edition. A draft saved without an edition keeps its artist (`ListingDraft.artist`).
- The real publish function must store a reason code for a listing error (`listings.error_message` is free text today); the detail screen shows `PublishFailure` codes it has words for.
- A question with a few actions to pick from ("camera or library?") uses the iOS action sheet through `chooseOne` in `src/services/choice-sheet.ts`; alerts are for confirmations and failures.
- Home screen is the listings tab with a three-tile summary on top. The connect-platforms screen is shown only once, after sign-up.
- The paywall appears when publishing the first listing, only to users without a plan.
- Design source of truth: the mockups and logo in `docs/design/` (tokens and type in its README). Figma is no longer used.
- Languages: European Portuguese (`pt-PT`, the source), Spanish and English. Strings live in `src/i18n/locales/`; the device language picks one, English is the fallback.
- v1.0 is light mode only (`userInterfaceStyle: "light"`).
- Two environments: `staging` (Supabase project "Valan Staging", ref `guinjxcsacyzqhmhpugf`) and `production` (Supabase project "Valan", ref `gjecpafvndblkwvcnqmg`), both in `eu-central-1`. Each is a separate Supabase project with its own keys and Edge Function secrets, and its own RevenueCat and marketplace credentials (eBay sandbox on staging; Discogs has no sandbox, so staging uses a test account with draft listings). Every change is deployed and checked on staging before production.
- Connecting a marketplace account is done by three Edge Functions. `connect-start` (needs a session) asks the connector to start, keeps the attempt in `connection_handshakes` and answers with the address where the seller approves. The marketplace sends the seller's browser to `connect-callback`, which finishes the attempt, stores the credentials and redirects to the app (`valan://connect?result=connected|denied|failed&marketplace=…`). `disconnect` (needs a session) deletes the connection. The marketplace credentials never reach the phone; the app treats the redirect as a hint and reads the state of the connection from the database.
- `connect-callback` is the only Edge Function without a session check (`verify_jwt = false` in `supabase/config.toml`): a browser coming from a marketplace carries no Valan session. What protects it is the state of the attempt: 32 random bytes, stored only as a SHA-256 hash, good for ten minutes, one pending attempt per seller and marketplace, and deleted in the same statement that reads it, so it works once. The seller and the marketplace of a connection come from the stored attempt, never from the request, and nothing of the request is copied into the redirect. No other function may be opened this way.
- Stored marketplace credentials are encrypted in the Edge Function (`_shared/token-cipher.ts`): AES-256-GCM, a fresh random IV for every value, and each value bound to its row and column (user id, marketplace and which secret it is, as additional authenticated data), so a value copied to another row or column does not decrypt. A stored value reads `<key version>.<IV>.<ciphertext>`; the version is what allows the key to be rotated. What a connection attempt keeps (for Discogs, the request token and its secret) is a credential too and is encrypted the same way. `connection_handshakes` is reached only by Edge Functions: the app's roles have no privilege on it and a restrictive policy that is never true.
- Function settings (Edge Function secrets in the dashboard on staging and production; `supabase/functions/.env` locally, never in the repository): `DISCOGS_CONSUMER_KEY`, `DISCOGS_CONSUMER_SECRET`, `CONNECTION_TOKENS_KEY` (32 random bytes in base64, a different one in each environment, from `openssl rand -base64 32`). Locally also `CONNECT_CALLBACK_URL=http://127.0.0.1:54321/functions/v1/connect-callback`, because inside the local stack the functions do not know the address the browser uses (the address must be https, or http on this machine: anything else is refused before a marketplace is asked), and optionally `APP_CONNECT_URL` (default `valan://connect`) to return to Expo Go. A marketplace whose keys are missing answers "unavailable"; nothing else breaks.
- The Discogs connector connects with OAuth 1.0a signed with PLAINTEXT over HTTPS, as Discogs documents it (https://www.discogs.com/developers, Authentication > OAuth Flow): request token with our callback, the seller approves on discogs.com, access token from the verifier, then `/oauth/identity` for the account name. Discogs access tokens do not expire, and there is no API to revoke one: disconnecting deletes our copy, and the seller can also remove Valan's access in their Discogs settings (the confirmation in the app must say so). Listings already published stay on the marketplace when an account is disconnected; Valan stops managing them.
- A connector is tested against hand-written answers through an injected `fetch`, never the live service, and its errors never carry a token, a secret or the marketplace's answer. `discogs.ts` implements connecting only; everything else answers `unsupported`, and it joins the full contract suite (`contract.ts`) when publishing is built.

## Do not

- Do not install new dependencies without asking.
- Do not edit migration files that have already been applied; always create a new migration.
- Do not read or write `.env` files.
- Do not commit directly to `main`.
- Do not write business logic or integration code without a failing test first.
